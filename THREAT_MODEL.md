# Модель угроз

## Модель продукта

Пользовательский HTTP-клиент → Go-сервер → локальный PostgreSQL. API и БД — разные процессы; только сервер принимает продуктовые команды. Значимые данные и последствия — [§5 паспорта](PROJECT.md#5-значимые-данные-и-другие-объекты).

**Объект EK1:** минимальный сервер на loopback, health-check с проверкой PostgreSQL и вымышленные экземпляры. Фактическое состояние и подтверждение запуска описываются в [PROJECT.md](PROJECT.md). Каталог через HTTP, вход, аккаунты, выдачи и возвраты пока планируются. Угрозы ниже явно рассматривают этот будущий API, кроме ошибок подключения и расхода ресурсов основы.

**Допущения:** демонстрация на одном доверенном компьютере, PostgreSQL не открыт в интернет; нет frontend, файловых загрузок, очереди, интеграций или публичной регистрации. Вымышленные данные не относятся к реальным студентам. Пользователь процесса и администратор БД доверены: захват их ОС/учётной записи не устраняется контролем HTTP-ролей. При этом сам HTTP-запрос недоверен даже с localhost. Loopback ограничивает сетевую экспозицию, но не заменяет вход и полномочия.

Сотрудник вправе описать состояние и получателя; приложение не может установить, правдиво ли он осмотрел или физически передал вещь. Намеренная ложь уполномоченного сотрудника — ограничение модели, а обход правил API и повторы его запросов входят в анализ. Перед переносом на другой компьютер/общую сеть нужно пересмотреть транспорт, доступ к БД, секреты и доступность.

## Границы доверия

| Граница | Что пересекает | Почему проверяем |
| --- | --- | --- |
| TB-1: HTTP-клиент → сервер | Сейчас health-check; в полном API пароль/токен, ID, фильтры, описание состояния | Клиент может подменить поля, вызвать любую операцию и повторить запрос |
| TB-2: сервер → PostgreSQL | Параметры SQL, результаты, изменения связанных записей | Проверка в Go не гарантирует целостность при нескольких запросах; значения не должны становиться SQL-кодом |
| TB-3: локальное окружение → процесс; процесс → ответ/журнал/Git | Строка подключения, ошибки, позже пароли/токены | Доверенная конфигурация может случайно попасть в публичный репозиторий или недоверенный ответ |

## Приоритет

**Высокий:** простое действие клиента или обычный повтор способен раскрыть чужую выдачу, дать лишние полномочия либо исказить ответственность. **Средний:** последствия значимы, но нужен дополнительный сбой обработки/публикации или нагрузка; локальность и учебные данные ограничивают ущерб. Числовую вероятность без измерений не назначаем.

Приоритетный набор: **T-01, T-02, T-04, T-05, T-06**. Это основные границы будущих чтений и изменений. Для каждой намечены решение и будущая проверка в третьем блоке. T-03/07/08 тоже связаны с решениями; меньший приоритет не означает принятия утечки или бессрочного ожидания.

### T-01

Анонимный клиент вызывает маршрут данных; вошедший участник перебирает ID выдач или передаёт чужого получателя в фильтре. При отсутствии проверки объекта получает сведения, кто чем пользуется.

**Граница:** TB-1, чтение каталога/выдач; планируется. **Приоритет:** высокий, выбран; подмена одного параметра реалистична и нарушает заданную приватность. [SR-01](SECURITY_REQUIREMENTS.md#sr-01), [SR-02](SECURITY_REQUIREMENTS.md#sr-02) → D-01.

### T-02

Участник вызывает запрос изменения каталога/выдачи/возврата или передаёт клиентскую роль сотрудника. Сервер, доверяющий полю роли или проверке только отдельных маршрутов, допускает изменение состояния от неуполномоченного пользователя.

**Граница:** TB-1, операции изменения; планируются. **Приоритет:** высокий, выбран; ложная выдача/возврат меняет ответственность, фронтенда для ограничения запросов нет. [SR-03](SECURITY_REQUIREMENTS.md#sr-03) → D-01.

### T-03

Команда случайно публикует пароль, рабочий токен или реквизиты окружения в истории Git/журнале. Человек с доступом к локальному HTTP API использует раскрытые реквизиты и действует от чужого имени; пароль БД обходит продуктовые полномочия при доступе к БД.

**Граница:** TB-3; реквизиты БД относятся к основе, аккаунты — к плану. **Приоритет:** средний; нужен доступ к утечке и локальному сервису. Вымышленные публичные fixtures не приравниваются к тайным реквизитам. [SR-04](SECURITY_REQUIREMENTS.md#sr-04) → D-01, D-03.

### T-04

Клиент сотрудника повторяет старое подтверждение возврата после ремонта и новой выдачи предмета. Если защита повтора проверяет только запись старой выдачи, отдельное обновление карточки снова меняет пригодность. Сбой между завершением выдачи и изменением карточки также оставляет противоречивый учёт.

**Граница:** TB-1/TB-2, возврат; планируется. **Приоритет:** высокий, выбран; повтор после сетевой ошибки обычен, а ложное состояние влияет на дальнейшую выдачу и ответственность. [SR-05](SECURITY_REQUIREMENTS.md#sr-05) → D-02. Проектный пограничный случай будет разобран в D-02 третьего блока.

### T-05

Два клиента сотрудника почти одновременно оформляют одну вещь; либо изменение её пригодности пересекается с выдачей. Раздельная проверка доступности и запись позволяют создать противоречивые выдачи или использовать устаревшее состояние.

**Граница:** TB-2, согласование изменений; планируется. **Приоритет:** высокий, выбран; возникает при обычной совместной работе, делает недостоверным ответ «у кого предмет». [SR-06](SECURITY_REQUIREMENTS.md#sr-06) → D-02.

### T-06

Клиент передаёт SQL-метасимволы в ID/описании или лишние служебные поля в JSON. Если сервер собирает SQL строкой либо без разбора переносит тело в запись, меняются чужие данные, роль или время возврата.

**Граница:** TB-1/TB-2, параметры будущего API. **Приоритет:** высокий, выбран; запрос полностью управляется клиентом, последствия могут затронуть весь учёт. [SR-07](SECURITY_REQUIREMENTS.md#sr-07) → D-03.

### T-07

Локальный скрипт отправляет слишком большое тело или запросы при недоступной БД. Без лимитов чтение/ожидание занимает память и подключения, очередной проверочный или рабочий запрос не завершается.

**Граница:** TB-1/TB-2; ожидание БД существует в основе, JSON-операции планируются. **Приоритет:** средний; публичного размещения нет, но ошибки клиента и локальная нагрузка возможны. [SR-08](SECURITY_REQUIREMENTS.md#sr-08) → D-03.

### T-08

Клиент получает сырой текст ошибки подключения через health-check или позднее через API. Строка подключения, детали SQL или токен в журнале раскрывают секреты и внутренние данные.

**Граница:** TB-3 → TB-1; ошибки БД относятся к основе. **Приоритет:** средний; воспроизводимо при неверной конфигурации, но внешняя экспозиция ограничена loopback. [SR-01](SECURITY_REQUIREMENTS.md#sr-01), [SR-04](SECURITY_REQUIREMENTS.md#sr-04) → D-03.
