# Подготовка защиты EK1

Показываем материалы репозитория. Основной рассказ — примерно три минуты, по минуте каждому; около трёх минут общего шестиминутного слота остаётся на адресные вопросы. Реальный слот и темп уточняются по объявлению преподавателя. Центральная цепочка M2 + M3 занимает до двух минут. Этот текст предназначен для подготовки; репетиция и человеческое понимание пока не подтверждены.

Перед использованием сверить [текущий статус и команды](PROJECT.md), зафиксированную версию, [вклад](CONTRIBUTIONS.md) и [использование ИИ](AI_USAGE.md). Запуск подтверждаем только по реально проверенной инструкции; не выдаём планы проверки механизмов за пройденные тесты.

Вспомогательные слайды: [PPTX](presentation/ek1.pptx), [PDF](presentation/ek1.pdf). M1 показывает 1–2, M2 — 3–4, M3 — 5–6.

## M1 — продукт, граница и основа

> «Инвентарь» учитывает вещи студенческого клуба. Сотрудник добавляет предмет, выдаёт его участнику и оформляет возврат. Участник видит каталог и свои выдачи. Важно сохранять достоверную ответственность: кому передали вещь и в каком состоянии её вернули.
>
> К EK1 подготовили Go-сервер, локальный PostgreSQL и учебные данные. Health-check работает и подтверждает доступ к базе; по запросу покажем запуск. Вход, роли, каталог и выдачи ещё не реализованы. Для них подготовили концепцию безопасности.
>
> Основная граница доверия — клиент и сервер. Запрос может содержать чужой ID или повтор старой операции даже на localhost. Loopback ограничивает сетевой доступ, но не проверяет полномочия. Дальше покажем, как повтор может незаметно испортить учёт.

Показ: [PROJECT.md](PROJECT.md), [модель и допущения](THREAT_MODEL.md#модель-продукта). По запросу — команда и ожидаемый ответ из PROJECT. Если запуск не спрашивают, оставить время для вопросов; не растягивать вступление.

## M2 — угроза и требование

> Приоритетная угроза T-04 — повтор старого возврата. Предмет вернули повреждённым, потом отремонтировали и выдали другому участнику. Клиент повторяет прежний запрос, например после потери ответа.
>
> Правдоподобное решение: обновлять выдачу только пока она не завершена. Старая запись действительно защищена. Но отдельное обновление карточки может снова поставить прежнюю непригодность. Проверка только старой выдачи пройдёт, хотя актуальные данные уже испорчены.
>
> Поэтому SR-05 запрещает при повторе любые изменения старой выдачи, карточки и новой выдачи. Проверять нужно все связанные записи после ремонта, новой выдачи и повтора, включая другое тело запроса. Это защита достоверности учёта. Такой повтор реалистичен, поэтому угрозу включили в приоритетный набор.

Показ: [T-04](THREAT_MODEL.md#t-04) → [SR-05](SECURITY_REQUIREMENTS.md#sr-05) → [разбор контрпримера](SECURITY_DECISIONS.md#уточнение-цепочки-по-контрпримеру).

## M3 — решение и будущая проверка

> В D-02 выбрали транзакцию с блокировкой экземпляра, затем выдачи. Выдача и изменение пригодности используют тот же порядок. Если возврат уже завершён, отвечаем конфликтом до любых записей. Иначе вместе сохраняем возврат и карточку; ошибка откатывает оба изменения.
>
> Альтернатива — условный SQL-переход: карточка меняется только если действительно завершилась выдача. Он компактнее, но сложнее читать и расширять. Выбрали явную последовательность для трёх сценариев; общая дисциплина блокировок нужна обоим вариантам.
>
> Будущие проверки — повтор старого возврата после ремонта и новой выдачи, сбой между записями, одновременные запросы. Они пока не выполнены: возврата в коде нет. Решение обеспечивает согласованность внутри БД; будущие внешние уведомления потребуют другого механизма.

Показ: [D-02 и сравнение](SECURITY_DECISIONS.md#d-02), затем его конкретные будущие проверки. Не показывать второе D вместо завершения одной цепочки.

## Вопросы для самостоятельной подготовки

Ответы ниже — опора для понимания, а не текст для чтения на защите. Каждый участник должен объяснить свой фактический вклад; публикация коммита не означает, что он разработал код или выполнил тест.

| Вопрос | Что нужно объяснить |
| --- | --- |
| Что сейчас работает? | Только подтверждённую основу из PROJECT; вход/каталог/выдачи не приписывать текущему коду |
| Почему localhost не заменяет вход? | Он ограничивает доступ с сети, но любой локальный HTTP-клиент может вызвать маршрут и подменить поля |
| Почему защищаем учебные выдачи? | Данные вымышленные, но архитектура должна соблюдать роли, приватность и достоверность ответственности полного продукта |
| Чем SR отличается от D? | SR задаёт наблюдаемое защитное поведение, D выбирает механизм и ограничения; проверка — способ позже подтвердить механизм |
| Чем T-04 отличается от обычной двойной выдачи? | Повтор не меняет уже защищённую старую запись, но портит другую актуальную запись после последующих действий |
| Почему общая транзакция может быть недостаточна? | Она атомарно сохраняет и правильные, и ошибочные изменения; побочный UPDATE нужно запретить при отсутствии перехода |
| Зачем одна блокировка экземпляра во всех операциях? | Блокировка только в возврате не согласует его с выдачей/ремонтом; общий порядок даёт определённый порядок изменений |
| Что обеспечивает уникальный индекс? | Только не более одной активной выдачи; он не проверяет пригодность и не предотвращает старый побочный UPDATE |
| Почему повтор отвечает 409? | Повтор не является новым допустимым переходом; неизменность состояния обязательна, одинаковый ответ исходного запроса — нет |
| Когда пересмотреть выбранное D? | При изменении сценария/поддержки условного SQL, выходе в общую сеть или появлении внешних побочных эффектов — по ограничениям соответствующего D |
| Откуда берутся пользователь и роль? | Из проверенной серверной сессии и аккаунта; не из `role` или ID текущего пользователя в теле запроса |
| Как честно назвать проверку, которой нет? | Будущая проверка с условиями и ожидаемым результатом; отдельный анализ не является запуском сценария |

До сдачи проверить маршрут ссылок, временной баланс трёх частей, запуск оцениваемой версии и самостоятельные ответы. При отдельном требовании презентации использовать тот же материал; слайды не заменяют комплект EK1.
