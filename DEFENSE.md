# Подготовка защиты EK1

Основной рассказ — примерно три минуты, по минуте каждому; остальная часть общего слота остаётся на адресные вопросы. Реальный слот уточняется по объявлению преподавателя, темп — на репетиции. На центральную цепочку M2 + M3 отводим до двух минут.

Перед использованием сверить [текущий статус и команды](PROJECT.md), зафиксированную версию, [вклад](CONTRIBUTIONS.md) и [использование ИИ](AI_USAGE.md). Запуск подтверждаем только по реально проверенной инструкции; не выдаём планы проверки механизмов за пройденные тесты.

Слайды: [PPTX](presentation/ek1.pptx), [PDF](presentation/ek1.pdf). M1 показывает 1–2, M2 — 3–4, M3 — 5–6. Связанные разделы репозитория держим открытыми для уточнений.

## M1 — продукт, граница и основа

> «Инвентарь» — сервис учёта вещей студенческого клуба. Сотрудник добавляет предмет, выдаёт его участнику и фиксирует возврат. Участник видит каталог и свои текущие и завершённые выдачи. Важно сохранять историю: кому передали вещь и какое состояние указали при возврате.
>
> К EK1 подготовили HTTP-сервер на Go, PostgreSQL и учебные данные. Маршрут `/healthz` проверяет соединение с базой. Вход, роли, каталог и выдачи ещё не реализованы; для них подготовлена концепция безопасности.
>
> Главная граница доверия — клиент и сервер. Даже локальный клиент может передать чужой ID или повторить старый запрос. Поэтому доступ через loopback не заменяет проверку полномочий. Дальше разберём риск повторного возврата.

Показ: [PROJECT.md](PROJECT.md), [модель и допущения](THREAT_MODEL.md#модель-продукта). По запросу — команда и ожидаемый ответ из PROJECT. Если запуск не спрашивают, оставить время для вопросов; не растягивать вступление.

## M2 — угроза и требование

> Угроза T-04 — повтор старого возврата. Предмет вернули повреждённым по выдаче L1, затем отремонтировали и выдали другому участнику по L2. Позже клиент повторяет старый запрос.
>
> Кажется, достаточно обновлять выдачу только пока она не завершена. Но если карточка предмета обновляется отдельной безусловной командой, повтор снова пометит предмет непригодным. L1 останется прежней, а карточка будет испорчена. Сравнение только L1 не заметит ошибку. Даже транзакция может вместе сохранить ошибочные изменения.
>
> Поэтому SR-05 требует при повторе сохранить без изменений L1, карточку и L2. Угрозу выбрали приоритетной: старый запрос способен испортить актуальный учёт уже после ремонта и новой выдачи. Далее — механизм защиты.

Показ: [T-04](THREAT_MODEL.md#t-04) → [SR-05](SECURITY_REQUIREMENTS.md#sr-05) → [разбор контрпримера](SECURITY_DECISIONS.md#уточнение-цепочки-по-контрпримеру).

## M3 — решение и будущая проверка

> Для SR-05 спроектировали транзакцию PostgreSQL. Выдача, возврат и изменение пригодности сначала блокируют строку предмета. Возврат затем блокирует выдачу и проверяет её состояние. Если она завершена, отвечаем 409 без изменений; иначе сохраняем возврат и карточку вместе.
>
> Альтернатива — условный SQL-запрос: карточка меняется только при новом завершении выдачи. Он компактнее, но явные шаги проще проверять и расширять в Go. Общая блокировка предмета нужна обоим вариантам.
>
> Граница решения — одна БД и общий протокол всех трёх операций. Будущая проверка: после возврата L1, ремонта и выдачи L2 повторяем старый запрос на возврат. Ожидаем 409 и неизменность всех трёх записей. Проверим также сбой между обновлениями и два одновременных возврата. Эти проверки ещё не выполнены: возврата в коде нет.

Показ: [D-02 и сравнение](SECURITY_DECISIONS.md#d-02), затем его конкретные будущие проверки. Не показывать второе D вместо завершения одной цепочки.

## Вопросы для самостоятельной подготовки

Ответы ниже — опора для понимания, а не текст для чтения на защите. Каждый участник должен объяснить свой фактический вклад; публикация коммита не означает, что он разработал код или выполнил тест.

| Вопрос | Что нужно объяснить |
| --- | --- |
| Что сейчас работает? | Go-сервер, пул PostgreSQL и `/healthz`. SQL применяется отдельно по инструкции; health-check проверяет соединение, но не наличие схемы. Входа, каталога и выдач ещё нет |
| Что подтверждают unit-тесты? | Ответы обработчика и настройки. Функция Ping в тестах подставная; реальное подключение и подготовка БД требуют отдельного запуска |
| Почему localhost не заменяет вход? | Он ограничивает доступ с сети, но любой локальный HTTP-клиент может вызвать маршрут и подменить поля |
| Почему защищаем учебные выдачи? | Данные вымышленные, но архитектура должна соблюдать роли, приватность и достоверность ответственности полного продукта |
| Чем SR отличается от D? | SR задаёт наблюдаемое защитное поведение, D выбирает механизм и ограничения; проверка — способ позже подтвердить механизм |
| Чем T-04 отличается от обычной двойной выдачи? | Повтор не меняет уже защищённую старую запись, но портит другую актуальную запись после последующих действий |
| Почему общая транзакция может быть недостаточна? | Она атомарно сохраняет и правильные, и ошибочные изменения; побочный UPDATE нужно запретить при отсутствии перехода |
| Зачем одна блокировка экземпляра во всех операциях? | Блокировка только в возврате не согласует его с выдачей/ремонтом. Общий протокол согласует изменения одного предмета; он обязателен для всех путей и не обещает отсутствие любых дедлоков |
| Что обеспечивает уникальный индекс? | Только не более одной активной выдачи; он не проверяет пригодность и не предотвращает старый побочный UPDATE |
| Почему повтор отвечает 409? | Повтор не является новым допустимым переходом; неизменность состояния обязательна, одинаковый ответ исходного запроса — нет |
| Что происходит при потере ответа? | Сбой между обновлениями требует отката. При потере связи во время COMMIT исход может быть неизвестен; успешную фиксацию потеря HTTP-ответа не отменяет. Проверяем состояние, повтор не меняет завершённый возврат |
| Может ли система установить, кто сломал вещь? | Она сохраняет сведения сотрудника. Физическую передачу и правдивость осмотра сама не проверяет |
| Когда пересмотреть выбранное D? | При изменении сценария/поддержки условного SQL, выходе в общую сеть или появлении внешних побочных эффектов — по ограничениям соответствующего D |
| Откуда берутся пользователь и роль? | Из проверенной серверной сессии и аккаунта; не из `role` или ID текущего пользователя в теле запроса |
| Как честно назвать проверку, которой нет? | Будущая проверка с условиями и ожидаемым результатом; отдельный анализ не является запуском сценария |

До сдачи проверить маршрут ссылок, временной баланс трёх частей, запуск оцениваемой версии и самостоятельные ответы. При отдельном требовании презентации использовать тот же материал; слайды не заменяют комплект EK1.
