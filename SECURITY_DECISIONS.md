# Проектные решения безопасности

Решения описывают будущие механизмы полного API. В EK1 не реализованы вход, роли, выдача и возврат; наличие сервера/БД не подтверждает их свойства. Статус основы и реально выполненных проверок — в [PROJECT.md](PROJECT.md). Указанные ниже проверки пока не выполнялись.

### D-01

**Серверная идентичность и полномочия.** Связи: [T-01](THREAT_MODEL.md#t-01), [T-02](THREAT_MODEL.md#t-02), [T-03](THREAT_MODEL.md#t-03) → [SR-01](SECURITY_REQUIREMENTS.md#sr-01), [SR-02](SECURITY_REQUIREMENTS.md#sr-02), [SR-03](SECURITY_REQUIREMENTS.md#sr-03), [SR-04](SECURITY_REQUIREMENTS.md#sr-04).

**Контекст и выбор.** Учебные аккаунты создаются вне API. В БД хранится Argon2id-хеш пароля с индивидуальной случайной солью; параметры фиксируются при реализации и проверяются по времени/памяти на демонстрационном компьютере. После входа сервер выдаёт непрозрачный случайный 256-битный токен сессии на один час; в БД хранится его хеш. Продуктовый обработчик получает ID и роль из серверной сессии/аккаунта, а не из клиентских полей. Открытый перечень маршрутов — только вход и health-check; новые маршруты по умолчанию требуют входа.

Запрос выдачи для участника обязательно ограничивается его ID на стороне сервера, в том числе в списках и фильтрах. Чужой и отсутствующий ID дают одинаковый 404. Для операций изменения сервер сначала проверяет сессию и роль сотрудника, затем разбирает бизнес-ввод; лимиты транспорта действуют независимо от доступа. Маршрутов назначения ролей и удаления истории нет. Поля JSON разбираются по [D-03](#d-03), но проверка полномочий действует независимо от правильности ввода.

**Почему так.** Непрозрачная сессия проста для одного локального сервера, позволяет истечение/отзыв без доверия утверждениям клиента. Фильтрация в запросе к БД уменьшает риск забыть отсечь чужие строки после чтения. Парольный хеш ограничивает последствия утечки таблицы; он не делает безопасным известный демонстрационный пароль.

**Ограничения.** Кража действующего токена даёт его полномочия до отзыва/истечения. ОС, администратор БД и честность сотрудника вне гарантии. Loopback выбран для демонстрации; при общей сети нужны защищённый транспорт и пересмотр эксплуатации. Параметры хеширования и ограничение попыток входа нельзя считать доказанными до реализации/проверки.

**Будущая проверка.** Создать A, B и сотрудника, по одной текущей/завершённой выдаче A/B. Проверить матрицу чтений и изменений по критериям SR-01–03; отдельно повторить с чужим ID, фильтром B и клиентским `role=staff`. Ожидание: чужие поля не выходят, запрещённые операции не меняют БД, разрешённые работают. Проверить истёкшую/отозванную сессию и, по SR-04, отсутствие контрольного пароля/токена в БД в открытом виде и журналах; токен допустим только в успешном ответе своего входа. Для хеша сверить соль разных аккаунтов, успешную проверку верного пароля и отказ неверного; это не измеряет устойчивость к произвольному перебору.

### D-02

**Единый переход учётного состояния.** Связи: [T-04](THREAT_MODEL.md#t-04), [T-05](THREAT_MODEL.md#t-05) → [SR-05](SECURITY_REQUIREMENTS.md#sr-05), [SR-06](SECURITY_REQUIREMENTS.md#sr-06).

**Контекст и выбранный механизм.** Возврат меняет не только выдачу, но и карточку; выдача зависит от пригодности и текущей занятости. Выбираем явную транзакцию PostgreSQL с блокировкой строки экземпляра. Все операции выдачи, возврата и изменения пригодности сначала блокируют этот же экземпляр. Затем возврат блокирует свою выдачу и проверяет, что она не завершена. Связь выдачи с экземпляром неизменна; поиск ID экземпляра до блокировки не даёт права записывать без повторной проверки. Единый порядок «экземпляр → выдача» исключает обратный порядок захвата в наших операциях.

Если возврат завершён, сервер возвращает 409 и не выполняет никаких записей. Иначе в той же транзакции сохраняет серверное время, состояние возврата и пригодность карточки. При ошибке выполнения до COMMIT откатывает обе записи; выдача и карточка фиксируются только вместе. Завершённые поля не редактируются отдельным маршрутом. У выдач также есть частичный уникальный индекс по экземпляру для строк без времени возврата: он страхует от двух активных записей, но сам не проверяет пригодность.

Потеря связи во время COMMIT может оставить результат неизвестным приложению; после восстановления связи нужно проверить сохранённое состояние. Потеря HTTP-ответа после успешной фиксации не отменяет возврат. Повторный запрос проходит те же проверки и не меняет уже завершённую выдачу или связанные записи.

При выдаче после блокировки сервер заново читает пригодность и отсутствие активной выдачи; занятый/непригодный предмет даёт 409. Обычное изменение карточки не завершает выдачу и не устанавливает независимый флаг «свободен». Доступность вычисляется из пригодности и активной выдачи. При конкуренции операций допустимый порядок задаётся захватом общей строки; изменение пригодности после выдачи не отменяет уже созданную ответственность.

#### Уточнение цепочки по контрпримеру

Это анализ проектного варианта, а не рассказ о найденном дефекте работающего кода или выполненном тесте.

**Правдоподобное исходное предположение:** условный `UPDATE loans … WHERE returned_at IS NULL` делает повтор возврата безопасным: завершённая запись не перезаписывается. Связь «T-04 → сохранность записи возврата → условное обновление → сравнить L1 после повтора» выглядит достаточной.

**Контрпример нашего продукта:** L1 возвращена повреждённой; после ремонта сотрудник выставил пригодность и оформил L2. Повтор старого возврата L1 не изменяет L1, но отдельный безусловный `UPDATE items` снова записывает старую непригодность. Сравнение только L1 проходит, а актуальная карточка искажена. Даже общая транзакция этого не исправляет: она может атомарно зафиксировать неправильный побочный эффект.

**Уточнение:** T-04 затрагивает связанные данные, SR-05 запрещает все побочные записи при повторе, D-02 допускает их только после подтверждённого нового перехода. Будущая проверка сравнивает L1, L2 и карточку до/после повтора, включая изменённое тело. Требовать одинакового HTTP-ответа при повторе не нужно: выбрали 409 с неизменным состоянием.

#### Сравнение двух способов обеспечить SR-05

| | Явная транзакция с блокировками — выбор | Единый условный SQL-переход — альтернатива |
| --- | --- | --- |
| Как защищает повтор | После блокировки проверяется незавершённость; при повторе выход до любых записей | Условное завершение выдачи возвращает строки через `RETURNING`; обновление карточки зависит только от этого результата. Ноль переходов — ноль побочных изменений |
| Атомарность | Все записи используют одну транзакцию; ошибка означает rollback | Все изменения в одном SQL-выражении атомарны; при ошибке выражение не фиксируется |
| Существенный компромисс | Ветвления/409 и расширение сценария читаются в Go, но требуется дисциплина общей транзакции и порядка блокировок | Меньше отдельных команд и сложнее случайно забыть условие, но связь записей скрыта в более сложном PostgreSQL-запросе; разбор ошибок и изменения сценария труднее |
| Граница гарантии | Другая ветка не должна обходить блокировку; отдельное подключение для карточки нарушит атомарность | CTE сам по себе не согласует возврат с ремонтом/выдачей. Альтернатива должна участвовать в том же протоколе блокировки экземпляра и не читать пригодность из устаревшего снимка |

Выбираем первый вариант для трёх простых сценариев и понятного общего протокола изменений. Единый SQL-переход остаётся применимым способом возврата при сохранении общего протокола. Выбор стоит пересмотреть, если возврат останется компактным стабильным переходом и поддержка одного условного запроса окажется проще при проверке; это не основание убирать блокировки связанных операций. Если появятся уведомления или другие внешние эффекты, ни один вариант не гарантирует их атомарность с БД: понадобится отдельное решение, а не отправка сообщения внутри транзакции.

**Будущие проверки механизма:**

1. По SR-05: подготовить L1 → повреждённый возврат → ремонт → L2; сохранить поля всех трёх записей; повторить L1 исходным и изменённым допустимым телом. Ожидание: 409, ни одна запись не меняется. Отдельно выполнить два одновременных возврата одной активной L1: только один меняет состояние.
2. В тестовом окружении вызвать ошибку после обновления выдачи, до обновления карточки. Ожидание: rollback обеих записей, выдача остаётся активной. Повтор после снятия сбоя успешно завершает её. Это будущая инъекция сбоя, не дефект для искусственного включения в продукт.
3. По SR-06: синхронизировать две попытки выдачи одного предмета; проверить ответы и частичный индекс. Затем пересечь выдачу с изменением пригодности в обоих порядках захвата общей строки; сверить фактический порядок и итог. Редактирование занятой карточки не создаёт вторую выдачу. Проверка только последовательных запросов не подтверждает эту гарантию.

**Ограничения:** блокировки могут ожидать; время ограничено [D-03](#d-03). Все изменения идут через один сервер/протокол; администратор БД может нарушить правила напрямую. Гарантии схемы, транзакций и сценариев пока не подтверждены реализацией. Историю следует сохранять и проверять после перезапуска; резервное копирование и восстановление после потери компьютера этим решением не обеспечиваются.

### D-03

**Ограниченная обработка HTTP-ввода и ошибок.** Связи: [T-06](THREAT_MODEL.md#t-06), [T-07](THREAT_MODEL.md#t-07), [T-08](THREAT_MODEL.md#t-08), [T-03](THREAT_MODEL.md#t-03) → [SR-07](SECURITY_REQUIREMENTS.md#sr-07), [SR-08](SECURITY_REQUIREMENTS.md#sr-08), [SR-01](SECURITY_REQUIREMENTS.md#sr-01), [SR-04](SECURITY_REQUIREMENTS.md#sr-04).

**Решение и обоснование.** SQL выполняется через параметры pgx; имена таблиц/столбцов не берутся из HTTP-ввода. Для каждой операции — отдельная структура JSON с запретом неизвестных полей и проверкой ID/срока/длин текста. Роль, ID текущего пользователя и время возврата клиент не назначает. Текст описания остаётся данными, без попытки удалить из него SQL-слова.

Для будущих JSON-операций тело ограничено 64 KiB; ожидание подключения и выполнение одной операции БД — общим контекстом до 2 с. Пул имеет конечный размер; сервер задаёт время чтения заголовков и корректно отменяет работу при разрыве запроса. Число соединений и остальные таймауты фиксируются при реализации по демонстрационному окружению. Текущие значения основы и её health-check берутся из кода/PROJECT, а не считаются уже равными этой будущей политике.

Клиент получает нейтральный код ошибки без сырого SQL/строки подключения. Журнал фиксирует операцию и категорию сбоя, исключает пароль, Authorization, тело входа и DATABASE_URL. Конфигурация приходит из окружения; локальные файлы секретов не отслеживаются. Удаление опубликованного секрета из текущего файла не устраняет историю: при утечке реквизиты нужно заменить.

**Будущая проверка.** По SR-07 отправить SQL-метасимволы, лишние служебные поля и некорректный ID; сверить БД и ответы. По SR-08 под сотрудником отправить в JSON-операцию 64 KiB + 1 байт и заблокировать доступ к БД/исчерпать пул: 413 без записи либо 503 после истечения общего контекста, затем восстановить БД и получить успешный health-check. По SR-04 использовать контрольные секреты и намеренную ошибку подключения; искать эти значения в ответах, журналах, текущем дереве отслеживаемых файлов и истории Git, не публикуя сам результат с секретами.

**Ограничения.** Параметризация не проверяет владельца — это D-01. Таймауты и лимит тела не защищают от любого числа параллельных соединений; при общей сети потребуются дополнительные ограничения. Нейтральный ответ снижает диагностичность: внутреннюю причину нужно различать безопасной категорией в журнале. Если публичное размещение/нагрузка станут частью продукта, пересматриваем эту политику.
