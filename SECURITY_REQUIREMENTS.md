# Требования безопасности

Эти требования относятся к планируемому полному API «Инвентаря». Основа EK1 ограничена локальным сервером, PostgreSQL и проверкой работоспособности; наличие основы не подтверждает выполнение требований входа, каталога и выдач. Фактический состав и запуск — в [PROJECT.md](PROJECT.md). Все проверки ниже пока являются критериями приёмки, а не результатами тестов.

Защищаем сведения о получателях, полномочия и достоверность учёта. Подмена возврата или получателя создаёт ложную ответственность; потеря истории скрывает незавершённую выдачу. Основания — [значимые данные паспорта](PROJECT.md#5-значимые-данные-и-другие-объекты).

### SR-01

**Закрытый доступ к данным.** До входа API не раскрывает каталог и выдачи; открыты только вход и проверка работоспособности.

**Приёмка:** запросы каталога/выдач без действующей сессии, с произвольным или истёкшим токеном получают 401 без предметных данных. Health-check не раскрывает строки БД, реквизиты или внутренние ошибки.

Связи: [T-01](THREAT_MODEL.md#t-01), [T-08](THREAT_MODEL.md#t-08) → [D-01](SECURITY_DECISIONS.md#d-01), [D-03](SECURITY_DECISIONS.md#d-03).

### SR-02

**Приватность выдач.** Участник читает только собственные текущие и завершённые выдачи; чужой ID или фильтр не расширяет доступ.

**Приёмка:** у A и B есть выдачи. Вход A и запрос чужого ID возвращают 404 без чужих полей; список A, в том числе с фильтром получателя B, не содержит выдач B. Сотрудник видит оба набора. Несуществующий и недоступный ID дают одинаковый публичный ответ.

Связи: [T-01](THREAT_MODEL.md#t-01) → [D-01](SECURITY_DECISIONS.md#d-01).

### SR-03

**Полномочия на изменение.** Только сотрудник меняет каталог и оформляет выдачи/возвраты. Клиент не назначает себе роль; ни одна роль не удаляет историю через API.

**Приёмка:** участник вызывает каждую операцию изменения, в том числе с `role=staff` в теле/заголовке, — 403, данные не меняются. Попытки назначить роль или удалить завершённую выдачу не имеют работающего API-маршрута и не меняют БД. Разрешённые действия сотрудника продолжают работать.

Связи: [T-02](THREAT_MODEL.md#t-02) → [D-01](SECURITY_DECISIONS.md#d-01).

### SR-04

**Нераскрытие секретов доступа.** Открытые пароли, токены сессий и реквизиты БД не публикуются в Git и журналах и не выдаются постороннему через HTTP. Новый токен возвращается только в успешном ответе входа своего аккаунта. В БД приложения нет открытого пользовательского пароля.

**Приёмка:** подготовить учётную запись и окружение с уникальными контрольными значениями. После входа и ошибки БД пароль и реквизиты БД отсутствуют в отслеживаемых файлах, HTTP-ответах и журналах. Выданный токен встречается только в успешном ответе входа, отсутствует в других ответах, Git и журналах. В записи аккаунта находится только парольный хеш. Явно обозначенные публичные вымышленные fixtures не считаются секретами и не доказывают защиту известных паролей.

Связи: [T-03](THREAT_MODEL.md#t-03), [T-08](THREAT_MODEL.md#t-08) → [D-01](SECURITY_DECISIONS.md#d-01), [D-03](SECURITY_DECISIONS.md#d-03).

### SR-05

**Целостность возврата и связанных данных.** Первое завершение выдачи согласованно сохраняет время/состояние возврата и пригодность предмета. Повтор завершённого возврата не меняет ни выдачу, ни карточку, ни более поздние выдачи.

**Приёмка:** возвратить L1 повреждённым, после ремонта отметить предмет пригодным, оформить L2 и повторить возврат L1, включая другое тело запроса. API возвращает 409; L1, L2 и карточка совпадают с состоянием до повтора. При сбое между записями первого возврата ни одна из них не фиксируется. Завершённая история сохраняется после перезапуска.

Это защита от ложного изменения ответственности и состояния, а не только удобство повторного запроса. Связи: [T-04](THREAT_MODEL.md#t-04) → [D-02](SECURITY_DECISIONS.md#d-02).

### SR-06

**Целостность выдачи.** Конкурентные изменения не создают две незавершённые выдачи одного экземпляра и не обходят его непригодность. Редактирование карточки не снимает текущую выдачу.

**Приёмка:** два запроса одного свободного предмета дают одну успешную выдачу и один 409; в БД ровно одна активная запись. Если перевод в непригодное состояние завершён до начала выдачи, выдача отклоняется. При конкуренции этих операций проверяется согласованный порядок: выдача либо предшествует переводу состояния, либо отклоняется после него. Редактирование занятой карточки не разрешает вторую выдачу.

Защитный смысл — достоверная ответственность за экземпляр и отсутствие обхода учёта. Связи: [T-05](THREAT_MODEL.md#t-05) → [D-02](SECURITY_DECISIONS.md#d-02).

### SR-07

**Недоверенный ввод не становится командой БД.** Параметры API не меняют смысл SQL и не позволяют записать служебные поля вне разрешённой операции.

**Приёмка:** строки с SQL-метасимволами в допустимых текстовых полях сохраняются буквально; некорректный ID, неизвестное поле или клиентское время возврата дают 400 без изменения БД. Схема и чужие записи остаются неизменными. Проверка доступа отдельно остаётся обязательной по SR-02/03.

Связи: [T-06](THREAT_MODEL.md#t-06) → [D-03](SECURITY_DECISIONS.md#d-03).

### SR-08

**Ограничение расхода ресурсов одним запросом.** HTTP-ввод и ожидание БД имеют конечные пределы, чтобы ошибочный или намеренно тяжёлый локальный запрос не занимал сервер бессрочно.

**Приёмка:** тело больше 64 KiB отклоняется с 413 до записи в БД. При недоступной БД или исчерпанном пуле ожидание одной операции ограничено 2 с; запрос завершается с нейтральным 503. После снятия нагрузки новый health-check успешен. Эти пределы не обещают доступность при произвольном объёме атак.

Связи: [T-07](THREAT_MODEL.md#t-07) → [D-03](SECURITY_DECISIONS.md#d-03).
